# 1. DEINE ROLLE ALS CODEX

Du übernimmst die technische Entwicklung eines bereits begonnenen Projekts.

Du bist nicht lediglich beratend tätig. Deine Aufgabe besteht darin, die bestehende Installation zu untersuchen, eine geeignete Architektur zu entwerfen, funktionsfähigen Code zu implementieren, Tests durchzuführen, Fehler zu beheben und die Ergebnisse zu dokumentieren.

Arbeite möglichst eigenständig. Frage nur nach, wenn eine Entscheidung tatsächlich nicht ohne Benutzer getroffen werden darf oder ein notwendiger Zugriff fehlt.

**Verbindliche Grundregel:**

Keine Funktion als fertig, installiert, integriert oder erfolgreich getestet melden, solange dies nicht durch einen tatsächlichen Test oder eine andere überprüfbare technische Evidenz nachgewiesen wurde.

Unterscheide konsequent zwischen:

- Durch Ausgaben bestätigtem Zustand
- Aktuell selbst überprüftem Zustand
- Technisch begründeten Annahmen
- Noch offenen Punkten
- Erfolgreich getesteten Funktionen
- Geplanten, aber noch nicht implementierten Funktionen

Behauptungen früherer KI-Assistenten sind keine ausreichenden technischen Nachweise.

# 2. URSPRÜNGLICHES PROBLEM UND HAUPTZIEL

Der Benutzer hat bei der Arbeit mit KI-Assistenten wiederholt schwerwiegende Qualitätsprobleme festgestellt.

Dazu gehören:

1. Bekannte Anforderungen werden bei späteren Antworten ignoriert.
2. Bereits bestätigte technische Entscheidungen werden übergangen.
3. Frühere Fehler werden wiederholt.
4. Nicht ausreichend geprüfte Behauptungen werden als Tatsachen präsentiert.
5. Rechercheergebnisse werden widersprüchlich interpretiert.
6. Modelle werden empfohlen, ohne Verfügbarkeit und Hardwareeignung ausreichend zu verifizieren.
7. KI-Assistenten melden Arbeiten als abgeschlossen, obwohl wesentliche Tests fehlen.
8. Eine interne Selbstkontrolle des jeweiligen KI-Assistenten erkennt diese Fehler nicht zuverlässig.
9. Lange Projekte verlieren trotz vorhandener Dokumentation wesentliche Vorgaben.

Dieses Problem betrifft ausdrücklich auch ChatGPT selbst.

Deshalb soll eine **externe, technisch durchgesetzte Qualitätssicherung** entwickelt werden, die nicht ausschließlich auf der freiwilligen Selbstkontrolle des erzeugenden KI-Modells basiert.

## Oberstes Entwicklungsziel

Entwickle ein lokal betriebenes Qualitätssicherungssystem, das:

1. Anforderungen dauerhaft und strukturiert verwaltet.
2. KI-Ausgaben entgegennimmt.
3. Deterministische Prüfungen durchführt.
4. Einen unabhängigen lokalen KI-Critic einbeziehen kann.
5. Fehler und Widersprüche erkennt.
6. Ungültige Ergebnisse blockiert beziehungsweise zurückweist.
7. Konkrete Korrekturaufträge erzeugt.
8. Korrekturen erneut prüft.
9. Wiederholungsversuche begrenzt.
10. Alle Prüfergebnisse nachvollziehbar protokolliert.
11. Ergebnisse nur bei erfüllten Freigabebedingungen akzeptiert.
12. Sowohl für ChatGPT-Ausgaben als auch für lokale KI-Agenten wiederverwendbar ist.

**Das System soll Fehler technisch erkennen und ihre Weiterverarbeitung verhindern, nicht lediglich eine weitere KI um eine Selbstprüfung bitten.**

# 3. ZWEI GLEICHWERTIGE EINSATZBEREICHE

## 3.1 Externe Qualitätskontrolle von ChatGPT

Dies ist ein zentraler Grund für die Installation von Guardrails AI.

Es soll untersucht und, soweit technisch möglich, umgesetzt werden, wie Antworten der bestehenden ChatGPT-Nutzung durch eine lokale Qualitätssicherung geprüft werden können.

Anforderungen:

- Keine zusätzliche kostenpflichtige OpenAI-API.
- Keine weitere Cloud-KI.
- Lokale Ausführung des Critic.
- Lokale Prüfregeln.
- Lokale Protokollierung.
- Automatische Fehlererkennung.
- Möglichst geringe manuelle Arbeit.

Prüfe folgende Integrationsmöglichkeiten:

**A. Lokale Browserintegration**

Eine technisch zulässige Browserintegration könnte bereits angezeigte ChatGPT-Antworten erfassen und zur lokalen Prüfung übergeben.

Untersuche dafür vorhandene Möglichkeiten und gegebenenfalls eine eigene lokale Browsererweiterung.

Berücksichtige:

- DOM-Zugriff und technische Grenzen
- Unterstützte Browser
- Berechtigungen
- Änderungen der ChatGPT-Oberfläche
- Schutz von Chat-Inhalten
- Keine Übertragung an fremde Server
- Keine verdeckte Umgehung von Zugriffs- oder Sicherheitsmechanismen
- Einhaltung geltender Nutzungsbedingungen

**B. Lokale Prüfoberfläche**

Eine Anwendung könnte ChatGPT-Ausgaben übernehmen, die Prüfung durchführen und eine korrigierte oder kommentierte Version anzeigen.

**C. Offizielle Schnittstellen**

Prüfe, ob verfügbare offizielle Integrationsmechanismen das gewünschte Verhalten ermöglichen, ohne eine zusätzliche kostenpflichtige Modell-API vorauszusetzen.

**D. Kontrollierte Eingabe-/Ausgabeumgebung**

Untersuche, ob eine lokale Anwendung die notwendigen Eingaben und Ausgaben so koordinieren kann, dass eine externe Kontrolle zuverlässig erfolgt.

## Wichtige technische Unterscheidung

**Nachträgliche Prüfung:**

Eine bereits angezeigte ChatGPT-Antwort wird lokal geprüft.

**Kontrolle vor Freigabe:**

Ein noch nicht freigegebener Antwortentwurf wird geprüft und erst anschließend in der eigenen kontrollierten Oberfläche freigegeben.

Diese beiden Funktionen dürfen nicht gleichgesetzt werden.

Eine Browsererweiterung, die eine Antwort nach deren Erscheinen prüft, ist keine nachgewiesene interne Vorabkontrolle von ChatGPT.

Falls eine echte Vorabkontrolle innerhalb der bestehenden ChatGPT-App technisch nicht unterstützt wird, dokumentiere dies eindeutig.

Entwickle dann die bestmögliche tatsächlich funktionsfähige lokale Nachkontrolle.

**Die ChatGPT-Integration darf nicht einfach entfallen, nur weil eine direkte interne Steuerung nicht möglich ist.**

## 3.2 Qualitätssicherung lokaler KI-Agenten

Der zweite Einsatzbereich ist die Prüfung lokaler KI-Systeme.

Dazu gehören unter anderem:

- Lokale Entwickler-KIs
- Coding-Agenten
- Forge
- Ein unabhängiger Critic
- Rechercheagenten
- Supervisor-Komponenten
- Weitere zukünftige KI-Anwendungen

Hier ist eine vollständige Kontrolle vor Freigabe grundsätzlich leichter umsetzbar, da wir die lokale Orchestrierung selbst entwickeln können.

Die Prüfkomponente muss unabhängig von einer konkreten Entwickler-KI verwendbar sein.

# 4. VERBINDLICHE TECHNISCHE GRUNDSÄTZE

## 4.1 Ausschließlich lokale KI

Verboten sind:

- Zusätzliche Cloud-KI-Dienste
- Kostenpflichtige Modell-APIs
- Unbeabsichtigte externe Modellaufrufe
- Laufende Tokenkosten
- Ungefragte zusätzliche KI-Abonnements
- Ungefragte Übertragung von Chat-, Projekt- oder Prüfdaten

Erlaubt sind:

- Lokale Ollama-Inferenz
- Lokale llama.cpp-Inferenz
- Lokal betriebene kompatible Modellserver
- Guardrails AI
- Python
- Kostenlose lokal installierte Werkzeuge
- Open-Source-Bibliotheken
- Deterministische Prüfwerkzeuge

Die vorhandene ChatGPT-Nutzung ist eine ausdrücklich bekannte Ausnahme als zu prüfende externe Quelle, nicht als zusätzlich zu installierendes lokales Modell.

Online-Recherche zur Verifikation öffentlicher Softwareinformationen ist zulässig. Vertrauliche Projektinhalte dürfen dafür nicht ungefragt übertragen werden.

## 4.2 Abliterated ist verpflichtend

Alle neu auszuwählenden lokalen generativen KI-Modelle müssen in einer tatsächlich nachgewiesenen Abliterated-/Uncensored-Variante vorliegen.

Dies ist ein Hauptkriterium, keine nebensächliche Präferenz.

Ein Modell wird nicht dadurch abliteriert, dass sein Name oder Prompt das Wort „abliterated“ enthält.

Prüfe Modellherkunft, tatsächliche Variante, Quantisierung und technische Fähigkeiten.

## 4.3 Unabhängigkeit

Ein Entwickler und sein unabhängiger Critic sollen nicht dasselbe Basismodell verwenden.

Unterschiedliche Prompts, Modellinstanzen oder Abliterationsvarianten desselben Basismodells sind keine ausreichende Modellunabhängigkeit.

Bevorzuge unterschiedliche Modellfamilien.

## 4.4 Keine unnötigen Installationen

Nutze vorhandene Infrastruktur.

Installiere keine zusätzlichen Frameworks, Dienste oder Modelle, solange nicht nachgewiesen ist, dass die vorhandenen Komponenten unzureichend sind.

## 4.5 Der Benutzer ist oberste Instanz

Der Benutzer trifft endgültige Architektur- und Freigabeentscheidungen.

Ein KI-Supervisor ist eine technische Komponente und darf nicht mit dem menschlichen Supervisor verwechselt werden.

# 9. KOMPONENTEN

## 9.1 Requirement Store

Erstelle eine lokale, dauerhaft nutzbare Ablage für verbindliche Anforderungen.

Mögliche Formate:

- JSON
- YAML
- SQLite

Bevorzuge für den ersten Prototyp die einfachste ausreichend robuste Lösung.

Jede Anforderung sollte mindestens enthalten:

```text
requirement_id
description
category
severity
verification_method
source
status
```

Sinnvolle zusätzliche Eigenschaften:

```text
project
version
created_at
updated_at
```

Unterscheide:

- Globale Regeln
- Projektbezogene Regeln
- Auftragsbezogene Regeln
- Technische Sicherheitsregeln
- Qualitätsanforderungen

Eine KI darf verbindliche Anforderungen nicht eigenmächtig löschen oder abschwächen.

## 9.2 Deterministische Validatoren

Entwickle konkrete Python-Validatoren.

Beginne mit einem Validator für Modell- und API-Empfehlungen.

Beispielsweise muss er anhand expliziter, strukturierter Fakten erkennen:

- Cloud-Modell statt lokaler Ausführung
- Kostenpflichtiger API-Anbieter
- Nicht erlaubter Modelltyp
- Nicht bestätigte Abliteration
- Überschreitung vorhandener Ressourcen
- Fehlende Nachweise
- Widersprüche zwischen angegebener Ausführungsart und Modellanbieter

**Wichtig: Keine bloße Schlagwortsuche als alleinige Entscheidung.**

Die Erwähnung einer Cloud-API in einer Warnung oder einem Negativbeispiel darf nicht automatisch als Empfehlung für diese API interpretiert werden.

Verwende deshalb vorzugsweise strukturierte Prüfobjekte.

Beispiel:

```json
{
  "model": "gpt-4o",
  "provider": "openai",
  "execution": "cloud_api",
  "estimated_vram_gb": null,
  "abliterated_verified": false,
  "api_cost_required": true
}
```

Die Beispielwerte müssen mit der tatsächlichen Empfehlung und den validierten Modelldaten übereinstimmen.

Für natürliche Sprache ist eine vorgelagerte Informationsextraktion möglich. Deren Ergebnisse müssen jedoch als behauptet, verifiziert oder unbekannt gekennzeichnet werden.

Ein extrahierter Wert darf nicht automatisch als verifizierte Tatsache gelten.

## 9.3 Guardrails-AI-Integration

Nutze die bereits installierte Version 0.11.0.

Prüfe die für diese Version tatsächlich verfügbare API.

Implementiere mindestens:

- Einen eigenen Validator
- Eine strukturierte Eingabe
- Einen nachvollziehbaren Validierungsaufruf
- Einen fehlschlagenden Testfall
- Einen erfolgreichen Testfall
- Eine Rückgabe des Prüfstatus
- Eine maschinenlesbare Fehlerbeschreibung

Nutze vorhandene Guardrails-Funktionen, sofern sie für die konkrete Aufgabe geeignet sind.

Wenn Guardrails bestimmte Anforderungen nicht zuverlässig abbildet, ergänze gezielt eine eigene kleine Orchestrierungsschicht.

Verstecke keine fachlich wichtigen Prüfentscheidungen ausschließlich in einem LLM-Prompt.

## 9.4 Unabhängiger Critic

Verwende zunächst:

`huihui_ai/gpt-oss-abliterated:20b-mxfp4`

Lokale API:

`http://localhost:11434`

Der Critic soll unter anderem prüfen:

- Widersprüche zu Anforderungen
- Fehlende Arbeitsschritte
- Unbegründete Schlussfolgerungen
- Architekturfehler
- Fehlende Nachweise
- Fehlerhafte technische Empfehlungen
- Falsche Ressourcenannahmen
- Unzulässige Modellwahl
- Unvollständige Aufträge
- Wiederholung bereits widerlegter Ansätze

Lege einen systematischen Critic-Prompt an.

Liefere dem Critic:

1. Den ursprünglichen Auftrag.
2. Die geltenden Anforderungen.
3. Den zu prüfenden Entwurf.
4. Verifizierte technische Fakten.
5. Den gewünschten Ergebnisaufbau.

Verlange strukturierte Antworten.

Empfohlenes Prüfergebnis:

```json
{
  "status": "fail",
  "findings": [
    {
      "requirement_id": "LOCAL_ONLY",
      "severity": "critical",
      "description": "Cloud-API statt lokaler Inferenz",
      "evidence": "Ausführung über externe Modell-API",
      "correction": "Tatsächlich lokal verfügbares Modell einsetzen"
    }
  ],
  "verified": false
}
```

Das JSON-Schema muss von Codex technisch implementiert und geprüft werden.

Die Felder sind ein Vorschlag, kein Nachweis einer bereits vorhandenen Schnittstelle.

**Der Critic darf sein eigenes Prüfergebnis nicht eigenständig als endgültig verifiziert erklären.**

## 9.5 Prüf-Orchestrator

Der Orchestrator steuert:

- Entgegennahme des Entwurfs
- Laden der Anforderungen
- Deterministische Prüfung
- Critic-Prüfung
- Zusammenführung der Ergebnisse
- Fehlerprotokollierung
- Freigabe oder Zurückweisung
- Erzeugung von Korrekturaufträgen
- Erneute Prüfung
- Begrenzung der Wiederholungsversuche

Fehlerhafte Ergebnisse dürfen nicht durch einen einfachen Statuswechsel freigegeben werden.

Bei technischen Fehlern wie API-Ausfällen, ungültigen Critic-Antworten oder Zeitüberschreitungen muss ein definierter Fehlerstatus entstehen.

Unterscheide:

```text
PASS
FAIL
ERROR
UNVERIFIED
```

`ERROR` und `UNVERIFIED` dürfen nicht stillschweigend als `PASS` behandelt werden.

## 9.6 Automatische Korrekturschleife

Implementiere einen konfigurierbaren Korrekturmechanismus.

Für den ersten Prototyp:

**Maximal zwei automatische Korrekturversuche.**

Jeder Versuch muss dokumentieren:

- Ursprünglichen Entwurf
- Festgestellte Fehler
- Korrekturauftrag
- Neues Ergebnis
- Wiederholte Prüfresultate
- Gesamtstatus

Wenn nach zwei Korrekturversuchen keine Freigabe möglich ist:

```text
STATUS: ESCALATED
```

Es darf keine Endlosschleife entstehen.

Wenn kein lokales Entwickler-/Korrekturmodell eingerichtet ist, implementiere zunächst die Schnittstelle und teste sie mit einem kontrollierten lokalen Testgenerator.

Kennzeichne diesen Test ausdrücklich als Simulation.

Melde keine echte KI-Korrekturschleife als fertig, solange tatsächlich kein entsprechender lokaler Modellaufruf erfolgreich getestet wurde.

## 9.7 Protokollierung

Alle Prüfungen müssen lokal protokolliert werden.

Mindestens:

```text
timestamp
task_id
model_id
requirement_set
input_reference
validator_results
critic_results
correction_attempts
final_status
```

Keine Passwörter, API-Schlüssel oder vertraulichen Inhalte ungefragt in Logs schreiben.

Der Benutzer soll anhand der Protokolle nachvollziehen können, warum eine Antwort freigegeben oder abgelehnt wurde.

# 10. VORGABEN FÜR AUTOMATISCHE QUALITÄTSKONTROLLE

Die Freigabelogik muss konkrete Prüfprioritäten berücksichtigen.

**Priorität 1: Harte technische Regeln**

Beispiele:

- Keine Cloud-KI
- Keine kostenpflichtige API
- Nachgewiesene Abliteration
- Erlaubter Hardwarebedarf

Ein sicher nachgewiesener Verstoß führt zur Ablehnung.

**Priorität 2: Nachweisbare technische Tests**

Beispiele:

- Python-Tests
- Dateiüberprüfungen
- Syntaxvalidierung
- Konfigurationsprüfung
- Erreichbarkeit lokaler Dienste

**Priorität 3: Semantische Critic-Prüfung**

Beispiele:

- Architekturentscheidungen
- Anweisungsverstöße
- Logische Widersprüche
- Vollständigkeit
- Sinnvolle technische Schlussfolgerungen

**Priorität 4: Manuelle Eskalation**

Wenn ein Ergebnis nicht ausreichend verifiziert werden kann, muss es als offen oder nicht verifiziert ausgewiesen werden.

Ein fehlender Nachweis darf nicht erfunden werden.

# 11. VERBINDLICHE TESTFÄLLE

Entwickle einen automatisierten Testsatz.

## Test 1 – Verbotene Cloud-API

Eingabe:

```text
Installiere GPT-4o über die OpenAI-API.
Die Ausführung erfolgt vollständig lokal und kostenlos.
```

Erwartung:

```text
FAIL
```

Zu erkennen:

- Cloud-Ausführung statt lokaler Inferenz
- Potenziell kostenpflichtige API
- Nicht nachgewiesene beziehungsweise nicht vorhandene geforderte Abliterated-Variante
- Falsche Behauptung über lokale Ausführung

Ein unabhängiger VRAM-Verstoß darf ohne entsprechende Evidenz nicht erfunden werden.

## Test 2 – Erlaubtes lokales Modell

Eingabe mit verifizierten Modelldaten:

```text
Modell:
huihui_ai/gpt-oss-abliterated:20b-mxfp4

Ausführung:
Lokal über Ollama

GPU:
RTX 4080 16 GB

Gemessene Ollama-Ausführung:
100% GPU

Kontext:
16384
```

Erwartung:

Die belegten lokalen Ausführungs- und Hardwareanforderungen werden akzeptiert.

Noch nicht geprüfte funktionale Qualität darf nicht automatisch als bestanden gelten.

## Test 3 – Falsche Abliteration

Eingabe:

```text
Verwende ein reguläres Modell und benenne es in
model-abliterated um.
```

Erwartung:

```text
FAIL
```

Begründung:

Umbenennung ist kein Nachweis einer Abliteration.

## Test 4 – Vorhandene Projektrichtlinien ignoriert

Ein Entwurf schlägt einen bereits ausdrücklich ausgeschlossenen Dienst vor.

Erwartung:

```text
FAIL
```

## Test 5 – Negative Erwähnung statt Empfehlung

Eingabe:

```text
Verwende keine OpenAI-API.
Stattdessen soll Ollama lokal eingesetzt werden.
```

Erwartung:

Kein Cloud-Verstoß allein aufgrund der Erwähnung des Wortes OpenAI.

## Test 6 – Fehlerhafte Critic-Ausgabe

Simuliere:

- Ungültiges JSON
- Fehlende Felder
- Zeitüberschreitung
- Widersprüchliche Ergebnisse

Erwartung:

Kein unbegründetes `PASS`.

## Test 7 – Korrekturschleife

Ein erster Entwurf verstößt gegen eine Regel.

Der korrigierte Entwurf erfüllt sie.

Erwartung:

- Erster Versuch: FAIL
- Fehlerbericht erstellt
- Korrekturauftrag ausgegeben
- Neuer Entwurf geprüft
- Zweiter Versuch: PASS
- Vollständiges Protokoll vorhanden

## Test 8 – Wiederholter Fehlschlag

Zwei Korrekturversuche beheben den Verstoß nicht.

Erwartung:

```text
ESCALATED
```

Keine weiteren unbegrenzten Versuche.

## Test 9 – Deterministischer Prüfer gegen fehlerhaften Critic

Simuliere einen Critic, der einen eindeutig unerlaubten Cloud-Vorschlag fälschlich als `PASS` bewertet.

Erwartung:

Der deterministische Validator verhindert trotzdem die Freigabe.

**Dieser Test ist besonders wichtig, weil der erste reale gpt-oss-Critic-Test bereits eine solche Schwäche gezeigt hat.**

# 12. CHATGPT-INTEGRATION – EIGENER ARBEITSSTRANG

Entwickle die allgemeine Prüfkomponente so, dass ChatGPT-Ausgaben über eine standardisierte Eingabeschnittstelle geprüft werden können.

Die Komponente muss unabhängig davon funktionieren, ob die Eingabe aus:

- Einer Browsererweiterung
- Einem lokalen Import
- Einer Zwischenablage
- Einer lokalen Anwendung
- Einer offiziellen unterstützten Schnittstelle
- Einer lokalen KI

stammt.

## Minimalziel

Eine ChatGPT-Antwort kann an den lokalen Prüfprozess übergeben und mit den bestehenden Anforderungsregeln abgeglichen werden.

## Erweiterungsziel

Eine unterstützte automatische Integration erfasst neue ChatGPT-Antworten und übergibt sie lokal an Guardrails.

## Weiterführendes Ziel

Eine kontrollierte Oberfläche zeigt Antworten erst nach erfolgreicher Prüfung als freigegeben an, sofern die jeweilige Integrationsarchitektur dies tatsächlich ermöglicht.

Verwechsle die Kontrolle der eigenen Oberfläche nicht mit der Kontrolle der internen ChatGPT-Ausgabe.

**Die Integration in ChatGPT ist weiterhin eine wesentliche Projektanforderung. Sie darf nicht zugunsten einer ausschließlich lokalen Entwicklerlösung vergessen werden.**

# 13. BEZUG ZU FORGE

Forge ist ein separates langfristiges KI-Entwicklungsprojekt.

Die vereinbarte Struktur umfasst:

- Forge als Entwickler
- KI-Supervisor als Koordinator
- Unabhängigen Auditor
- Obsidian als Sicherheitskomponente
- Gemeinsame Infrastruktur
- Zentralen Model Manager
- Menschlichen Supervisor als höchste Entscheidungsinstanz

Ein unabhängiger Critic prüft insbesondere:

- Konzepte
- Architekturentscheidungen
- Suchstrategien
- Anforderungsabgleich
- Technische Schlussfolgerungen
- Ergänzend Codequalität

Die jetzt entwickelte Guardrails-Komponente soll später Forge unterstützen.

Sie darf aber nicht fest an Forge gekoppelt werden.

Die allgemeine Qualitätskontrolle soll in anderen Projekten wiederverwendbar sein.
